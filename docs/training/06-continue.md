# 6. Resume, migrate and collaborate

[Learning guide](README.md) · [Previous: review](05-review.md)

**Outcome:** you can extend the work without losing decisions, repeating discovery or confusing frontend and backend responsibilities.

## Resume the existing engagement

Give the agent the same private folder and selected package source. Ask it to inspect current intent, source identity and stage status before acting. A focused fix should reuse valid decisions; a material change should recheck the affected evidence and requirements.

> Resume [existing engagement] using [selected package source]. Keep the chosen experience and verified metric definitions. Fix [observed issue] in [specific destination or journey]. Inspect the affected dependencies, propose only material missing decisions, and review the changed behavior plus anything it can affect. Preserve unrelated work and report what remains unobserved.

New CLI engagements use bounded specialist context: the orchestrator retains the full record while each worker gets relevant evidence, shared promises and exact references. Completed work can be reused when its bindings remain current. Do not send every specialist the full conversation or launch a replacement for a task whose state is uncertain.

These mechanics preserve work and constrain repeated context. They do not guarantee a particular token bill or justify weaker models, lower quality or omitted review. Actual savings need attributable host usage.

## Migrate an existing experience

Start with one coherent source scope and preserve the original experience's obligations. Supply available definitions, screenshots or exports, calculations, filters, actions, security behavior and result examples through approved channels. Keep original IDs and source versions.

The artifact translator and selected source specialist distinguish:

- What the supplied material actually captures.
- What requires an authorized source API/export operation.
- What must be rebuilt or redesigned explicitly in Omni.
- What remains unknown or unsupported and needs review.

The same A–F sequence applies. Screenshots help communicate layout; they do not prove formulas, security or interactions. A connected source tool does not establish every capture operation or an end-to-end migration path. Check the [migration matrix](../../README.md#choose-a-workflow) and [source coverage](../parser-coverage.md) for the selected platform.

> Use [source artifact/export] to migrate [scoped analytical experience]. Inventory its calculations, filters, interactions and access behavior. Preserve source IDs and separate verified behavior from missing evidence. Follow A–F, compare three viable directions and wait for my selection. Reuse the existing Omni model where it meets the requirements; return specific backend gaps rather than rebuilding it by default.

Keep page-precise report obligations separate from interactive dashboard behavior. SSRS, Power BI paginated and extracted Crystal Reports evidence route through report-specific specialists and the Reports Beta foundation.

## Continue from Data Model Accelerator

Data Model Accelerator handles backend entities, grain, relationships and semantic modeling. This package handles the analyst-facing experience. Neither is required to redo the other's completed work.

| Situation | Next action |
| --- | --- |
| Existing Omni model supports the question | Reuse it and qualify the queries; a warehouse rebuild is unnecessary |
| A metric, relationship or field is missing | Send a scoped request with affected decisions, source identities, grain, security needs and acceptance criteria |
| A backend candidate returns | Retain its version and limitations, reconcile changes and revalidate affected queries/access before dependent work resumes |
| A DMA continuation is supplied | Follow the linked continuation protocol before generic initialization; initialize or resume the linked engagement once |

A backend candidate is not proof of deployed Topics. A prepared handoff is not proof that the receiving host was dispatched. Continue only through actually available tools and permissions; preserve pending deployment or access work explicitly.

Use the [backend collaboration how-to](../HOW_TO.md#work-with-data-model-accelerator) and [continuation protocol](../../skills/omni-backend-handoff/references/dma-continuation.md) for the exact route. Do not create a duplicate engagement or broaden semantic-only work into an unrequested frontend build.

## Resolve common first-run problems

| Symptom | Check next |
| --- | --- |
| The agent starts coding immediately | Confirm the selected orchestrator and current A–F state; recover missing analysis, choice or design evidence before dependent work |
| The App feels like generic dashboard tiles | Compare it with the captured outcome and experience promise; inspect complete journeys and return the specific composition/interaction gap to design |
| The logo or imagery is missing | Check the selected asset, source permission, loading path and placement, rather than assuming the website URL chose everything |
| Numbers or connections fail | Recheck user access, query/field bindings, source evidence and the native data-input contract before changing the presentation |
| Results feel stale | Separate source age, Omni query caching and the client display state; implement only the recorded refresh policy |
| The assistant repeats questions or rereads everything | Confirm it resumed the same engagement and that scoped task packets contain the current decisions and usable baseline |
| Every review says “passed,” but nobody rendered it | Separate source evidence from visual/runtime evidence and retain unobserved cases |
| A tool or library is unavailable | Record the capability gap and use permitted source/design work; do not auto-install or bypass an approval boundary |

## Finish the learning path

For your first engagement, be able to show:

- The audience, decision, selected source and actual access context.
- One finding with supporting evidence and a visible limitation.
- Three concrete concepts and your recorded selection.
- A full journey that expresses the agreed quality and brand choices.
- Current review evidence, remaining gaps and the intended publication boundary.
- A clear way to resume or request a backend change without starting over.

That is the ramp-up goal: knowing what to ask for, what to expect and how to judge the result. For detailed commands and platform routes, continue to the [operator how-to](../HOW_TO.md).

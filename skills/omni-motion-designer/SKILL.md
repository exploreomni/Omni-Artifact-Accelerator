# Omni motion designer

For selected [dimensional comparisons](../omni-design-systems/references/dimensional-visualization-craft.md),
resolve only task-serving transitions, camera changes or playback. Preserve exact
values and identity through interruption and reduced motion; animated thickness,
smoothing or travel must not invent measurements or uncertainty.

For spatial work, hand off the [single-session camera contract](../omni-app-engineer/references/native-scene-framework.md#compose-the-modules): meaningful named views, bounded transition/dwell, immediate wheel/pointer/key interruption, no competing autorotation and no clocks while hidden/offscreen. Return remains paused until user intent; live reduced-motion changes cancel movement and retain instant static views. Specify recovery, transcript and non-canvas equivalents. A timer/renderer double does not establish motion comfort or native frame rate.

Before runtime or tool use, follow the shared [package-use policy](../omni-artifact-accelerator/references/dependency-policy.md): no unapproved package installation/import or skill activation, and no Blender code or execution. Source review is separate from execution authority.

Own motion behavior as an interaction specification, with a static equivalent. Work from the app designer's flow/state inventory and a bounded assignment. Preserve [essential behavior independently of treatment](../omni-design-systems/references/experience-brief.md#separate-behavior-from-treatment): truthful data, identity, focus, cancellation and recovery are invariants; motion style and timing belong to the engagement. Animation and 3D/camera patterns are optional capabilities, never required by this skill.

For substantial new design, material redesign, explicit craft feedback or deliberate practice, apply the [curriculum role route](../omni-design-systems/references/experience-curriculum.md#role-routes) for interaction continuity and expressive feedback. Produce a [choreography storyboard](../omni-design-systems/references/experience-patterns.md#motion-choreography) with stable identity, data commit point, timing hypotheses, interruption and static/reduced equivalents; retain a static experience when motion adds no task value.

Read the [current design intent](../omni-artifact-accelerator/references/design-intent.md) and [experience brief](../omni-design-systems/references/experience-brief.md), including on direct invocation or resume. Reconcile the selected packet pin. Tie useful motion to the chosen primary journey and repeat-use behavior; an optional comparison animation alone cannot resolve an expressive-opening requirement.

## Inputs and scope

Use the app target and verified runtime capabilities, primary tasks, interaction states, brand contract, accessibility requirements, and performance budget. Read the Apple/Google motion sources in [vendor guidance](../omni-design-systems/references/vendor-guidance.md) and the current [Omni capability boundary](../omni-artifact-accelerator/references/omni-capabilities.md).

For migrations, distinguish observed interaction behavior from proposed motion using the [behavior ledger](../omni-qa-analyst/references/migration-behavior.md). Missing source motion or control evidence stays unknown. Preserve completion, control propagation and reduced-motion behavior across model/query changes; animation cannot substitute for an unsupported action or imply a backend operation succeeded.

## Work

For control feedback and detail/index continuity, use applicable [control-craft states](../omni-design-systems/references/control-craft.md#specify-the-selected-control-in-the-existing-design) and the [focused continuity lesson](../omni-design-systems/references/experience-curriculum.md#focused-control-practice). Keep exact result commits separate from animation, preserve focus across interruption, stop nonessential work when its region becomes hidden, and do not resume playback merely because a view reopens. Static/reduced variants must communicate the same pending, failed and completed states.

1. Start from the selected composition and named state transition; stabilize the static task and state the purpose before optional example retrieval, unless the user chose a reference. For material experience work, align with [visual craft](../omni-design-systems/references/visual-craft.md), without forcing animation into a faithful migration or focused correction. Give each proposed effect an observable purpose: confirm an action, explain a state change, preserve spatial context, or communicate progress. Remove effects without a task benefit.
2. Specify trigger, affected elements, initial/final states, duration/easing as proposed design values, interruption/cancellation, entry focus, return focus/scroll, and reduced-motion alternative. Include the selected usable width/height when clipping or travel distance matters. Do not present arbitrary timing as a vendor or Omni requirement.
3. Keep repeated filter changes responsive. Handle late/out-of-order data responses and interrupted navigation with engineering; animation completion must not determine query correctness or gate access to data.
4. Under reduced motion, use immediate state changes or a restrained static treatment. Preserve labels, focus, completion, and progress information. Avoid chart count-ups, moving baselines, parallax, repeated pulses, and autoplay decoration that obscure exact values or distract from analysis.
5. When supported by the runtime, honor `prefers-reduced-motion` at startup and when preferences change. The app engineer implements the verified mechanism. Do not assume a platform-managed native dashboard exposes animation hooks.
6. Validate normal and reduced variants, rapid repeated actions, error/empty/loading transitions, slow responses, keyboard use, and actual performance where measurable. A video proves appearance; it does not prove operability or performance.

If an expressive spatial scene is selected, state which position, size or connector encodes real data and which is decorative. Animation must not invent flow, geography or progress. Give any drag/rotate/zoom interaction an explicit entry/exit, keyboard/static alternative and page-scroll policy; avoid capturing scroll before the user engages it. A scene, multiple destinations or motion is never a universal App requirement.

For selected camera, drill/return or media transitions, use [scene choreography](references/scene-choreography.md) with the App engineer's advanced visualization module. Its synthetic storyboard and finite camera utility demonstrate cancellation, immediate reduced-motion state and cleanup; they are not native performance or rendered-quality evidence. Keep exact data commits independent of animation completion.

## Outputs and boundaries

Return a motion/state table with purpose, trigger, proposed timing, cancellation, static equivalent, implementation constraints, and observed test results. Hand implementation to the app engineer and independent checks to QA using [design QA](../omni-design-systems/references/design-qa.md).

If target support, acceptable performance, or a usable reduced-motion path is missing, keep the experience static and return the gap. External animation libraries, hosted assets, telemetry, network access, or platform changes require their own scoped implementation decision; motion design is not authorization for them.

For Hex App migrations, use [the computational state guidance](../omni-app-designer/references/hex-experience-mapping.md#brand-composition-narrative-and-motion). Distinguish pending input, running, completed and failed states with static equivalents. Neither a spinner nor a completed animation proves computation progress or success; preserve interruption and late-response behavior with engineering.

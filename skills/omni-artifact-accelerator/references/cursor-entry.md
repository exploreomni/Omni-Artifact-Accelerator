# Start an artifact engagement in Cursor

Open the selected Accelerator checkout with **File → Open Folder** and start a fresh Agent chat. Give Agent the business request and any approved source material. The checkout ships a short **Always Apply** project rule so the first message can be plain English, even with no file open. It directs Agent to the shared orchestrator and source specialist. Cursor reads referenced files on demand. [Project rule](../../../.cursor/rules/omni-artifact-entry.mdc) · [Cursor project rules](https://cursor.com/docs/rules)

If the user opened the parent workspace in the [local quick start](../../../README.md#quick-start), the starter message explicitly names the child checkout’s `AGENTS.md`. Read its linked orchestrator and run the helpers from that checkout. This path does not depend on automatic discovery of the child's project rule.

When working from a private engagement, keep its files in a sibling folder. To work with both folders in one window, add the real checkout and the intended engagement as workspace folders. Include only one Accelerator revision in that workspace. Opening a customer folder alone or pasting a repository URL does not establish that Cursor loaded the checkout's rule. Use real paths for the checkout, engagement and helper inputs. The package rejects symlink paths, and copying or linking the rule alone leaves its checkout-relative references unresolved in a customer repository. [Cursor multi-root workspaces](https://cursor.com/changelog/04-24-26) · [Repository engagement entry](engagement-entry.md)

For a skills-only installation, use the host-entry preflight to identify the available orchestrator and its revision. If project-rule discovery is the behavior under test, open the checkout containing the rule. An installed skills folder by itself does not supply a workspace project rule. [Host-entry preflight](engagement-entry.md#inspect-the-host-entry-first)

## Check the first response

In a fresh Agent chat, ask to migrate an existing Domo Pro Code App 1:1 and name two controls from that App. Give only the business request. Agent should recognize preservation, retain both controls, identify the available source evidence, and offer one source specification for confirmation. It should ask for only the material evidence missing from the authorized source route. A redesign is a separate user decision. Review against the [shared intake](work-intent.md) and [source comparison](migration-fidelity.md).

If the chat starts coding from the description or offers three designs, inspect the following before continuing.

1. Confirm the checkout and revision in the active workspace. From that checkout, use `git rev-parse --show-toplevel` and `git rev-parse HEAD`. In **Customize → Rules**, look for the project rule `omni-artifact-entry` and check **Always Apply**. Glob-scoped rules need a matching file in context, and manually invoked rules need a mention. [Cursor rule types](https://cursor.com/docs/rules)
2. Inspect the active team, project and user rules and any root `AGENTS.md` or `CLAUDE.md` in the workspace. Cursor gives team rules priority, followed by project and user rules. If an enabled team instruction conflicts with the migration workflow, identify the exact conflict for its owner. For ambiguous multi-root behavior, repeat the plain-English prompt in a fresh chat opened on the checkout alone. [Cursor rules and precedence](https://cursor.com/help/customization/rules)
3. Inspect the chat's file reads against the selected checkout. As a diagnostic, explicitly mention `@omni-artifact-entry` and ask which workflow files Agent can read. Record this as a manually assisted trial. For a blind retest, start another fresh chat without that mention. Retain the actual first response, Cursor version, workspace roots, source revision and observed reads. A local rule check verifies the shipped files. Only an actual Cursor session can establish observed host behavior. [Host entry checks](engagement-entry.md#inspect-the-host-entry-first)

# Omni 3D modeler

For a selected [dimensional visual](../omni-design-systems/references/dimensional-visualization-craft.md),
own justified geometry, hierarchy, fidelity and useful inspection views. Ordinary
bar/trend design remains with the designers. Separate constant decorative depth
from measured axes; a rendered illustration is not a data-linked chart runtime.

Own the spatial model and its design rationale. Work from a bounded assignment or a standalone brief. Select 3D when shape, adjacency, assembly, movement or spatial context helps the task; ordinary charts remain with the analyst and dashboard/App designers. An attractive scene alone does not establish analytical value or an expert modeling result.

## Start from the task

Reuse the current intent, authorized references, target surface and prior selections. If the brief only says “make it 3D,” recover the intended task first: what should someone inspect, understand or compare? Ask one consequential question when the answer cannot be inferred, while preparing an explicitly illustrative shape/interaction proposal. Choose routine camera, composition and material treatments yourself. Missing dimensions do not justify presenting invented measurements as a faithful replica.

Use the mode that resolves the actual need; no project must complete all four:

- **Create an object:** silhouette, part hierarchy, dimensions, surface treatment and inspectable detail for an original product or vehicle.
- **Compose an environment:** modular structure, spatial hierarchy, landmarks and useful views for a building, venue or operational setting.
- **Adapt an asset:** preserve authorized source identity, rights and scale; propose only necessary changes against the supplied evidence.
- **Review or revise:** locate the consequential geometry, meaning or inspection failure and check the affected correction.

Read [modeling judgment](references/modeling-judgment.md) for the selected mode and [brief and handoff](references/brief-handoff.md) when preparing a reusable model or engineering assignment. Use the relevant [3D curriculum](../omni-design-systems/references/3d-curriculum.md) for a demonstrated craft gap or deliberate practice; course consumption is optional.

## Resolve and hand off

For original procedural work, apply [procedural craft](references/procedural-craft.md): silhouette, meaningful hierarchy, material scale, optional context and purposeful views. The [native scene framework](../omni-app-engineer/references/native-scene-framework.md) supplies a bounded native-scene-v1 contract separate from SceneSpec 1. Choose scene-only illustration, governed spatial analysis or isolated asset processing from the task. Decorative entities need no dummy queries; analytical identities need the analyst's explicit mapping. Reuse the customer's brand and fidelity decisions rather than asking engine or wiring questions.

Establish units, axes, origin, fidelity and evidence before adding detail. Keep stable object/part IDs separate from names, array order and metric values. Specify an original component hierarchy, meaningful dimensions, material intent and named inspection views. Decorative lighting must not change the meaning of analytical color. Where data is linked, the analyst owns entity keys, grain, aggregation, scope and missingness; do not invent query bindings.

Resolve one useful `entry → inspect/select → exact evidence → return` path with the App designer. Preserve camera/selection on ordinary data refresh, with explicit reset and recovery behavior. Include a list or exact-value route to the same information; tours need static stops and interruption rules. The motion designer owns choreography; the app engineer owns viewer loading, disposal, input handling and native capability qualification.

Deliver the portable brief, neutral geometry/parameter description, asset provenance, identity mapping requirements and design rationale. Record unknowns and proposed versus verified dimensions. Reference existing design/QA records when present; no new approval lifecycle is created. Review one representative assembly before expanding detail, using only permitted observation methods. Independent [spatial QA](../omni-qa-analyst/references/spatial-qa.md) owns checks against original evidence; self-review remains labeled.

## Execution and surface boundaries

Choose the execution route before requesting infrastructure. For an original illustrative scene or animation authored as part of a native App, hand off bounded geometry/parameters to the App engineer for the [native browser route](../omni-app-engineer/references/spatial-integration.md#select-the-execution-route). A separate modeling VM is not a universal prerequisite for native App 3D. Inspect the actual target capabilities, review authored code and preserve package approval; do not assume a CDN or host-provided library is approved for this project. Use the optional isolated compiler route when off-browser asset processing or model compilation is actually needed. Never route untrusted scripts or arbitrary model imports into the App to bypass the compiler's denial.

- **No Blender code:** no source snippets, APIs, scripts, add-ons, copied/reconstructed node setups or implementation-derived algorithms. Do not execute or import `.blend` files. Optional conceptual study never authorizes those routes.
- **No package installation or library import/loading without explicit user sign-off.** Existing packages, samples, examples, scripts and permissive licenses do not confer approval. Follow the shared [dependency policy](../omni-artifact-accelerator/references/dependency-policy.md) when available; these restrictions apply even when that sibling reference is absent.
- The modeling harness is an optional, separately obtained tool, not part of this skill's installed runtime. Obtain its operator-supplied location, actual contract version and approved capabilities before serializing executable work. Never infer a repository path from the installed skill folder. Without that evidence, continue with the local portable brief; do not invent SceneSpec fields or run generated code.
- This guidance alone supplies no approved isolation runner for off-browser model processing. Treat generated scene data and supplied assets as untrusted; engineering owns the selected native App review or isolated compilation/quarantine/promotion path. Modeler output cannot grant itself approval or publish itself.
- Native Omni Apps are the intended integration surface when selected. A native dashboard remains a dashboard: route proposed spatial content through the BI engineer's verified native capabilities, retain unsupported requirements explicitly and do not substitute an App by implication.

Source/specification review, local computation, permitted rendering, native interaction and participant evidence establish different things. Report unavailable lanes as unrun; a valid file, generated GLB or successful upload does not prove polished rendering, safe execution or native delivery. Standalone use remains useful without a harness or sibling specialists: return the model brief and smallest unresolved capability/data requirement.

# Portable model brief and handoff

This is a human-readable handoff, not a strict SceneSpec schema or an execution request. It works without a repository checkout or modeling runtime. Extend the engagement's existing design, asset, data and QA records rather than creating competing copies.

| Decision | Record what is known |
| --- | --- |
| Task and surface | Audience, useful inspection/comparison, original request, selected App/dashboard surface and any preserved source behavior. |
| Fidelity and evidence | Schematic/illustrative/source-constrained rationale; verified versus invented/unknown dimensions; authorized reference origin and intended accuracy. |
| Coordinates and hierarchy | Units, axes, origin, parent/part relationships, stable IDs, meaningful dimensions and local transform intent. |
| Geometry and materials | Original shapes/curves, bounded repetition and surface intent; which details support the task; required imported assets and alternatives if unsupported. |
| Identity and data | Object IDs versus source entity keys; required mapping, grain, filter scope, units, denominators and missing/partial/restricted states. Analyst confirms meaning; the modeler does not fabricate bindings. |
| Inspection and return | Named view purposes, selected evidence, focus/list route, camera/selection retention, explicit reset, tour interruption and reduced/static behavior. |
| Assets and rights | Source/creator, access date, allowed use, attribution, original bytes/hash when available, transformation history, texture/external-resource needs and unresolved rights. Free access is not a reuse license. |
| Limits and capability | Selected execution route (authored native scene, approved library/asset, or isolated compilation), target usable dimensions/device constraints, proposed complexity, unsupported operations, approval coverage and exact runtime/schema evidence if any. |
| Delivery and review | Candidate/source/expectation versions, owner handoffs, output paths, observed checks, unrun lanes and the smallest outstanding requirement. |

For a real asset, keep the original and adapted candidate distinct. For a fictional specimen, label its measurements and content synthetic. Do not include credentials, sensitive query rows or confidential customer assets in reusable examples. Do not claim a generated file, hash or signature proves rights, safety or native behavior.

## Optional harness integration

This section applies to off-browser compilation. An original procedural scene authored in a native Omni App follows the [native integration route](../../omni-app-engineer/references/spatial-integration.md#select-the-execution-route) and needs no fictional VM/promotion receipt. Preserve the same identity, fidelity, input bounds and review requirements; missing compiler infrastructure must not unnecessarily block native scene design. Package imports and tenant writes still require their own authority.

The installed skill does not locate, install or activate a harness. An operator supplies the separately obtained harness location and version, its actual SceneSpec contract, approved dependency/operation scope, input limits and output profile. Read that contract only when integration is in scope. Its existence does not authorize execution.

Before serializing a candidate, map the brief to the **actual** supported contract and state omissions or adaptations. Preserve authoring parameters, stable IDs, units and provenance through the mapping. Do not invent fields, query IDs, extensions, asset URLs or executable expressions to fill gaps. Unsupported geometry remains a proposed requirement or an explicitly selected approximation; its absence is not silently accepted.

The intended safe handoff is bounded scene data to a fixed reviewed compiler, then quarantined output validation and exact-byte promotion. Arbitrary generated JavaScript, package resolution, plugins and Blender files are outside this route. No approved isolation runner is supplied by these documents. Follow the shared [dependency policy](../../omni-artifact-accelerator/references/dependency-policy.md) and existing host-owned authorization; `approved: true` inside an agent file grants nothing.

When the actual harness profile supports them, request an editable parameter source, model asset, identity mapping and provenance/validation receipt. Name the observed output format and limitations; do not promise GLB export or import compatibility before verification. App engineering consumes only the promoted bytes through a separately qualified viewer/data bridge. The modeling worker receives no Omni credentials or live data by implication. Publication remains a separate authorized operation.

## Recover without restarting

If only an image or vague idea is supplied, infer a provisional subject and identify the consequential missing task/fidelity evidence; continue a labeled illustrative proposal. If an existing decision or asset is already selected, reuse it. If the runtime is absent, return this brief and the unsupported mapping needs. If native dashboard support is unknown, preserve that target and ask the BI engineer for the specific capability evidence; do not turn the request into an App or external site.

On revision, state which object IDs, geometry, parameters, mappings or dependencies changed and which prior evidence is affected. Preserve unaffected design choices and original source requirements. Independent verification should derive expected dimensions/counts/values from the brief and source, not from the compiler's result alone.

# Omni app designer

Own the experience specification: how an intended user moves from a question to an informed action. Work from a bounded orchestrator assignment or directly on a standalone app brief. Separate [essential behavior, engagement-specific treatment and optional capabilities](../omni-design-systems/references/experience-brief.md#separate-behavior-from-treatment); shared behavior does not prescribe a shell or composition.

For substantial new design, material redesign, explicit craft feedback or deliberate practice, apply the [curriculum role route](../omni-design-systems/references/experience-curriculum.md#role-routes) for composition and interaction architecture. Resolve a task-appropriate path and screen relationship using relevant [experience structures](../omni-design-systems/references/experience-patterns.md#experience-structures), specifying the useful evidence gained, preserved context, responsive behavior and recovery in the existing design handoff.

Resolve the [shared experience brief](../omni-design-systems/references/experience-brief.md) in the selected design: original request, observable behavior, first encounter, repeat-use route, destination purpose/action/evidence, art direction and useful detail. Compare frontend treatments of the same task and retain their tradeoffs. On direct invocation or resume, reuse the current named choices rather than restarting discovery.

## Inputs

Use the audience and tasks, delivery mode, metric/query contract, security roles, source interaction inventory for migrations, accepted brand contract, and available target capabilities. Reuse existing decisions. For direct invocation too, read the [current design intent](../omni-artifact-accelerator/references/design-intent.md), its brand/assets and unresolved requirements; a missing required choice is a dependency, not permission to invent a substitute. A focused change reuses the selection without reopening unrelated intake. Native **Omni Apps** is the default app target; an external app is a separate explicit choice. Read [Omni capabilities](../omni-artifact-accelerator/references/omni-capabilities.md) and [design foundations](../omni-design-systems/SKILL.md).

For migration, read [behavior coverage](../omni-qa-analyst/references/migration-behavior.md). Track each source placement, query/control effect, persona and operational handoff; distinguish observed layout from a proposed composition. Missing Sigma layout/control context stays unknown, and missing explicit route holds dependent target design. A semantic or physical gap returns through the BI engineer and backend cowork workflow rather than being concealed by a new UI.

## Work

For control choice, search, restored input or responsive columns, use the relevant [control-craft decisions](../omni-design-systems/references/control-craft.md) in the existing design handoff. Distinguish draft/applied/restored input, local versus governed search, partial versus excluded selection and focus/return. Select the simplest adequate semantics; a styled dropdown does not automatically need a custom combobox. Use [focused curriculum practice](../omni-design-systems/references/experience-curriculum.md#focused-control-practice) only for the demonstrated gap.

For new concepts or material workflow redesigns, use the shared [ideation playbook](../omni-design-systems/references/ideation-playbook.md) to clarify assumptions, compare useful alternatives, and choose proportionate prototype fidelity. Reuse prior discovery. A small edit or faithful migration does not require new ideation or another approval for authorized reversible work.

For composition, navigation, adaptive behavior, or recovery changes, decide the task, evidence relationship and design rationale first, then retrieve only relevant [app patterns](references/app-patterns.md) or examples to resolve a specific uncertainty. A user-selected reference can lead this process. Examples are optional evidence, not a shell to fill. Read the linked usability guide when preparing a task test.

For substantial App design, preserve the user's intended first encounter and repeat-use experience using the [experience-mode decision](references/app-patterns.md#choose-the-experience-mode). An immersive brand request must remain visible in the entry composition, imagery/type roles and primary journey; do not quietly translate it into compact analytical density. Record actual destinations and preserved state when the chosen concept has separate screens.

1. Define the primary workflow and entry/return points. Keep a compact decision path for viewers and an inspectable path for analysts; do not add authoring controls to a viewer-only experience.
2. Map screens and interactions to the governed workbook/query contract. State filter scope, reset behavior, selection persistence, navigation, refresh, drill behavior, and URL/share state only where the target supports them.
3. Draft a coherent composition with an obvious analytical focus, contextual controls, responsive layout, and readable data density. Record usable **width × height**, host chrome/zoom assumptions, first-view priorities and intentional scroll regions using [available-space rules](references/app-patterns.md#design-for-the-space-the-app-actually-gets). Resolve wrapping and long labels without hiding essential scope or reducing the entire interface. Apply the accepted brand contract and only the relevant [vendor recommendations](../omni-design-systems/references/vendor-guidance.md).
4. Specify loading, empty, restricted, error, stale, and partial states. Preserve last-known data only when clearly labeled and authorized; never disguise permission failures as “no results.” Define keyboard/focus behavior and equivalent access to chart values.
5. For migrations, retain traceability to source controls, interactions, and intentional departures. A visual improvement does not authorize changing a business rule. Route ambiguous behaviors to the translator and orchestrator.
6. Produce reviewable screens or a prototype that tests the material uncertainty. For substantial new work or redesign, use [visual craft](../omni-design-systems/references/visual-craft.md) to resolve geometry/type/spacing and the meaningful detail/return path. Record a reasoned direct choice or compare compositions when that resolves a real uncertainty; no fixed concept count or novelty requirement applies. A color variant or prose concept does not establish a rendered visual comparison. Record findings separately from proposed revisions; if no users have tested it, mark usability untested. Select relevant [design QA](../omni-design-systems/references/design-qa.md), then hand implementation to the app engineer and motion details to the motion designer when needed.

Review one [first complete journey](../omni-design-systems/references/experience-brief.md#build-the-first-complete-journey-early) in the assembled candidate before expanding substantial work. Use the analyst's [coverage map](../omni-data-analyst/references/analytical-coverage.md) so richer content supplies valid comparisons and useful evidence. Engineering owns critical native-capability qualification; keep unresolved dependencies and useful fallbacks explicit. Give every consequential destination a critique disposition before claiming the experience complete, using only permitted observation methods. Declare applicable contexts and evidence lanes in the current requirements, and explicit journeys where interaction matters; derive review obligations before collecting captures. A correction needs a retest of that same destination/context or journey. Retain the full selected inventory when a focused edit reviews only affected obligations.

Use the selected identity asset in the representative screen with realistic labels/values, type roles, a useful primary action and consequential state. Label any provisional placeholder; confirm its native loading and critical runtime mapping with engineering. After implementation, review actual native wide/narrow captures and material engineering deviations against both the original named requirements and the selected design. Link observations to requirement/context IDs and current candidate/assets; a general craft pass cannot close an uninspected requirement. Record corrections, accepted adaptations and revised-candidate retests. Preserve selected scope and meaningful focus; a detail action must add useful verified evidence or an operation. Prototype success is separate from native craft and independent QA.

Hand off explicit destination, stable selection, entry focus, return focus/scroll and reset behavior; include a short-height case when the host constrains it. Engineering owns the [native data-input contract](../omni-app-engineer/references/native-data-input.md); exported or simulated rows do not prove a callback shape. If a demo uses renamed content, preserve the [authorized source/display mapping](../omni-branding/references/demo-presentation.md) in labels, detail and current dependencies. Neither a brand request nor a display name changes source identity or metric meaning.

## Outputs

Return a screen/flow specification, component and state inventory, data/interaction bindings, responsive/focus rules, annotations, target capability gaps, and review evidence. Include the brief, concept rationale, or usability test card only when relevant. Include exact artifact paths and accepted versus proposed decisions. Prototype records and generated example data must be visibly synthetic.

## Boundaries

Do not change semantic models, invent app APIs, add external dependencies or network calls, or publish/share by implication. A prototype must not imply that writeback, downloads, navigation, authentication, or embeds are supported until their contracts are verified. Continue unaffected design work when a required behavior is blocked and return the smallest unresolved decision to the orchestrator.

For Looker-to-App work, read [the App design mapping](references/looker-to-app.md). Use the same governed metric and source behavior contracts while designing task flows, controls and states. A source dashboard grid is evidence of prior organization, not an App layout requirement. Keep App-specific acceptance independent of dashboard receipts.

For Hex, read [the experience mapping](references/hex-experience-mapping.md). Distinguish Classic and Generative evidence, pending inputs from applied results, and UI state from governed computation. Preserve the full task through run/recompute, failure and reset; retain separate dashboard and App obligations when both are selected.

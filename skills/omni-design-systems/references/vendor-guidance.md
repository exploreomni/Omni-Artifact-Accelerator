# Vendor guidance and applied design decisions

Checked **2026-10-21**. These are primary vendor sources, deliberately combining design documentation with articles and design stories. Links support the source guidance in their row; the applied guidance is this package's recommendation for analytics work. Recheck current documentation for changing APIs, product features, standards, and asset terms.

This is not a composite Apple/Google/Microsoft/Samsung theme. Keep the customer's identity and Omni's interaction conventions. Do not copy proprietary fonts, icons, artwork, mobile measurements, materials, or animation systems without appropriate scope and rights. Native-platform point/dp measurements are not interchangeable with web CSS pixels.

## Use the guidance in a task

For discovery and concept comparison, load the [ideation playbook](ideation-playbook.md). For implementation-facing design decisions, load only the selected [app patterns](../../omni-app-designer/references/app-patterns.md) or [dashboard patterns](../../omni-dashboard-designer/references/dashboard-patterns.md). Use [usability testing](../../omni-qa-analyst/references/usability-testing.md) to distinguish a plausible design from observed comprehension.

Each applied pattern retains the user problem, when it helps or harms, a worked example, rationale, source/evidence type/platform/check date, target capability mapping and verification. Examples in this package are synthetic recommendations, not vendor templates or participant research. Platform-specific components and implementation instructions remain examples; verify Omni support separately. Recheck source/version when changing a pattern or making a feature-sensitive decision. Record inaccessible material or conflicting advice; prefer the guidance that fits the task and document why. Existing guidance below remains useful for visual and accessibility details.

## Web acceptance baseline

[WCAG 2.2](https://www.w3.org/TR/WCAG22/) is the normative accessibility reference, separate from vendor inspiration. Relevant checks include text contrast (1.4.3), non-text contrast (1.4.11), color independence (1.4.1), keyboard access (2.1.1), focus visibility (2.4.7), focus not obscured (2.4.11), reflow (1.4.10), and target size (2.5.8), including their exceptions. For AA, typical text needs 4.5:1 contrast and large text 3:1; essential component boundaries and graphical information need 3:1 where applicable. Target size has a 24-by-24 CSS-pixel minimum or spacing/other exceptions. A larger 44-by-44 touch target can be a project recommendation, not a misstatement of the AA rule.

An audit must record applicable criteria, tested surfaces, exceptions, results, and limitations. These selected checks do not establish full conformance. In platform-managed areas, record the limitation and verified alternative; do not silently change the selected deliverable to meet it.

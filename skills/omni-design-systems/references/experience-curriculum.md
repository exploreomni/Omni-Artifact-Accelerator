# Data Experience Design Studio

A shared curriculum for creating distinctive, useful Omni dashboards and analytical Apps. Use it for substantial new design, a material redesign, explicit craft feedback, or deliberate practice. A focused fix uses the relevant lesson only. A faithful migration retains its original behavior obligations.

The curriculum is an agent operating resource: selected lessons, original exercises, critique and revision. Installing it makes the guidance available; demonstrated competence requires reviewed work. Do not claim that installation retrained a model, trained every worker, or guarantees a polished result.

## The standard

Aim for a recognizable point of view, precise analytical communication and satisfying interaction. A convincing experience gives the audience something to understand or do that a generic arrangement of metrics and charts would make harder. Craft can be quiet, expressive, dense or spacious. Choose deliberately.

Define a **design thesis** before resolving a substantial composition:

> For [person and situation], organize [specific evidence] as [visual structure] so they can [decision/task]. Express [brand qualities] through [type, geometry, spacing, imagery and interaction]. The distinctive element is [useful focal treatment or interaction]. Its cost is [tradeoff]; use [simpler alternative] if [condition].

“Premium,” “modern,” rounded cards, a logo and a palette do not fill these blanks. An original thesis is also not an obligation to invent a new chart. A well-resolved table or bar chart may be the strongest choice.

## How agents use the curriculum

1. Read the brief, current design intent and the role route below. Identify the missing skill or uncertain decision; load those lessons and related pattern cards.
2. Make the smallest useful artifact: a chart specimen, composition, storyboard, query contract or implementation slice. For substantial visual alternatives, vary structure and behavior using the same data; color variants are not divergent concepts.
3. Use a worked [studio](experience-studios.md) when learning a technique. Use the real engagement when applying it. Keep synthetic exercises separate from customer evidence.
4. Have a different reviewer apply the [anchored critique](experience-review.md). Correct the most consequential craft weakness and review the changed artifact. Record what changed and why.
5. Bring the selected design through the existing [resolved handoff and designer return](visual-craft.md). Persist the findings in the engagement's current design/QA records; do not introduce a parallel approval lifecycle.

For normal work, this is a short targeted loop, not a requirement to complete every course module. For explicit training, progress through the shared foundation, the role specialization and an assessed capstone. Reuse an existing qualified example when its task, data and target still apply.

If rendering is unavailable or the user prohibits it, produce the best authorized specification/code and mark visual and native interaction evidence `not_run`. Keep moving on analytical, structural and source checks. A written storyboard or local controller rehearsal cannot establish visual polish. A CLI-only constraint is compatible with this curriculum; it changes which evidence can be collected.

## Curriculum

Each studio has a question, an exercise and a reviewable output. Lesson numbers are routing IDs, not a fixed project schedule.

| ID / studio | Skill to develop | Deliberate practice and review output |
| --- | --- | --- |
| S1 — Visual observation and abstraction | Explain why a composition works, beyond naming its colors or chart type. | Deconstruct an authorized reference into focal point, comparison, reading order, encoding, interaction and emotional tone. Identify one quality to transfer and one to avoid. Recreate the principle with original content; retain private source provenance. |
| S2 — Analytical intent and evidence shape | Match design to a decision, grain, denominator, uncertainty and comparison. | Turn an ambiguous brief into three answerable questions. For each, specify unit of analysis, required fields, missing data and a useful comparison. Reject an attractive but unsupported inference. |
| S3 — Art direction and composition | Give the experience a visual identity and information architecture. | Resolve two structural directions for the same scope: for example an annotated evidence essay and a comparison atlas. Specify dominant element, supporting regions, type roles, rhythm and density. Explain the tradeoff and select a direction. |
| S4 — Advanced visual encoding | Select a visual grammar that exposes a particular relationship. | Compare two encodings from the [pattern atlas](experience-patterns.md). Work with skew, ties, negatives, missing values and long labels. Show the exact insight each exposes or obscures; specify scales, ordering, labels and evidence access. |
| S5 — Editorial storytelling | Build an evidence-led sequence without inventing causality. | Write a question, supported finding, annotation and next investigation. Bind each statement to fields, filters and denominator. Make the text still truthful after a scope change or withhold it. |
| S6 — Dashboard composition | Deliver a scanable analytical argument with depth. | Compose overview, comparison and diagnostic detail with intentionally unequal emphasis. Finish chart titles, axes, units, labels and filter context. Demonstrate how the composition adapts using verified native settings. |
| S7 — App interaction architecture | Make exploration feel coherent and task-specific. | Design an investigation path using comparison, pinning, temporal exploration or narrative steps as justified. Specify useful outcomes, preserved context, keyboard route, return path and recovery. A drawer that repeats a number does not count as useful detail. |
| S8 — Motion and expressive feedback | Use timing and continuity to explain change and convey character. | Produce a storyboard with before/pending/after/interrupted states, object identity, trigger, choreography and reduced-motion equivalent. Implement one meaningful transition when supported. Assess a static version alongside it. |
| S9 — Brand, type and asset direction | Translate identity into a recognizable design language. | Reuse or ask for the company website and authorized assets. Resolve logo variants, typographic contrast, density, imagery, chart semantics and motion character. Show a specimen with a real selected asset and realistic labels; record font fallback and image provenance. |
| S10 — Engineering for craft | Preserve the design under real data and asynchronous execution. | Implement a representative slice from actual query/state contracts. Handle stable keys, late results, interrupted motion, formatting, loading and overflow. Return exact code/version evidence and deviations to the designer. |
| S11 — Inclusive and resilient experience | Keep the same analytical task available across input modes and states. | Use narrow layouts, zoom, keyboard, non-color cues, chart alternatives, missing data, restricted results and reduced motion. Record observed outcomes separately from specifications and unrun cases. |
| S12 — Critique, revision and transfer | Explain quality with evidence and reuse learning without freezing a house style. | Compare candidate against its thesis and intent; identify specific defects, revise and retest. Complete a second-domain exercise so the first successful layout does not become a universal template. |

S1–S5 form the shared foundation. S6–S10 are specialization studios. S11–S12 accompany the relevant practical work. Start with an exercise that addresses the demonstrated weakness; do not require experienced agents to repeat a complete foundation for every task.

## Role routes

All 13 roles participate in craft, with different responsibilities. A role may be performed inline; this table does not require spawning 13 agents.

| Role | Priority studios | Concrete contribution and handoff |
| --- | --- | --- |
| `omni-artifact-accelerator` | S1–S3, S6/S7, S12 | Route the brief by task and surface, retain the thesis and chosen alternatives, assign one owner for each shared decision, and ensure engineering returns to the designer. Keep training, artifact quality and release status separate. |
| `omni-data-analyst` | S2, S4, S5, S11 | Supply grain, denominator, uncertainty and independent expected values. Explain the comparison that would change a decision and the conclusion the data cannot support. |
| `omni-bi-engineer` | S2, S4, S6, S10 | Bind each encoding to exact fields, sort, grouping and filter semantics; qualify native chart/control support; provide a truthful alternative for an unsupported form. |
| `omni-dashboard-designer` | S3–S6, S9, S11, S12 | Resolve a dashboard composition, chart anatomy and reading path. Show how visual hierarchy follows the analytical question instead of using a default card grid. |
| `omni-app-designer` | S3–S5, S7–S9, S11, S12 | Resolve a distinctive task path, screen relationship and signature interaction with useful detail, preserved context and responsive state behavior. |
| `omni-app-engineer` | S7, S8, S10, S11 | Implement the selected interaction/motion from verified runtime contracts; preserve numerical truth and object identity; return deviations and exact-candidate evidence. |
| `omni-data-storyteller` | S2, S4, S5, S7 | Build evidence-bound headlines, annotation layers and narrative steps; state when narrative changes or disappears under filtering. |
| `omni-motion-designer` | S3, S7, S8, S10, S11 | Choreograph orientation, selection, comparison and feedback; supply timing hypotheses, cancellation behavior, static/reduced equivalents and the observation needed to judge the result. |
| `omni-branding` | S1, S3, S9, S11 | Turn official assets and brand character into a coherent visual direction across type, layout, imagery and behavior; keep categorical/semantic colors independent of decoration. |
| `omni-design-systems` | S1, S3, S4, S8–S12 | Maintain reusable visual/motion primitives and examples across different directions; prevent accidental drift without forcing every domain into the same composition. |
| `omni-qa-analyst` | S2, S4, S8, S11, S12 | Critique exact artifacts independently, reconcile numbers and interaction intent, and distinguish code/specification evidence from rendered, native and human observations. |
| `omni-artifact-translator` | S1, S2, S4–S7, S12 | Capture the source's visual grammar, hierarchy, navigation and narrative intent alongside its semantics. Preserve source behavior; distinguish adaptation from an authorized redesign. |
| `omni-backend-handoff` | S2, S4, S7, S10 | Turn a proposed encoding/interaction's missing grain, stable ID or measure into a bounded model requirement. Ask for the minimum data needed; leave craft choices with the frontend. |

## From inspiration to original design

Study a curated example because its problem resembles the current one, not because it is popular. Identify evidence type: source description, static image, observed interaction or measured task result. A gallery listing is only a discovery lead. A source claiming an interaction is different from an interaction we ran.

Translate the observation into a neutral design rule and an original specimen. Record source URLs, creator, checked date, observation limits and rights in the engagement's research evidence. Keep product/vendor names, copied layouts, slogans, datasets and third-party assets out of generated customer experiences unless specifically authorized. Inspiration does not grant reuse rights or establish Omni capability. This curriculum's pattern names and practice datasets are original teaching material.

## Completion and continued use

Use the [practice progression](experience-review.md#practice-progression), not a claim that all agents have been trained. A useful training result includes the brief, artifact/version, critique, revision and unresolved limitations. Add lessons from an actual reviewed failure to a relevant pattern or exercise; avoid turning every local preference into a universal rule. Keep customer work out of the skill package.

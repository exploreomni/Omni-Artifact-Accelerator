# Omni design systems

Own the shared visual and interaction contract across the engagement. Work from the orchestrator's bounded assignment or a direct request; do not spawn a team for a token or component decision. Keep [essential behavior separate from visual treatment and optional capabilities](references/experience-brief.md#separate-behavior-from-treatment); reusable state/interaction rules may support different renderers without becoming an App shell.

For substantial new design, material redesign, explicit craft feedback or deliberate practice, apply the [curriculum role route](references/experience-curriculum.md#role-routes) and selected [studios](references/experience-studios.md). Develop reusable relationships among type, spacing, encoding, motion and states; demonstrate the selected treatment and compare specimens when that resolves uncertainty. Carry relevant rules into the existing design contract without forcing every domain into one composition.

Use the [shared experience brief](references/experience-brief.md) to connect the original request to observable behavior, destination purpose/action/evidence and responsible roles. Carry brand qualities into concrete composition, type/image hierarchy and state rules. Keep the selected direction in the existing design/intent records; use the [context-transfer studio](references/experience-context-studio.md) when the gap is losing those choices during handoff.

## Inputs and boundaries

Read the engagement brief, selected surface, accepted brand answers, source artifacts, and existing component or theme system. Reuse established decisions and the [current design-intent selection](../omni-artifact-accelerator/references/design-intent.md); changes to shared tokens/assets must reach each affected surface and reopen its relevant visual checks. For standalone use, establish the audience, decision/task, target surface, and available source of truth before designing.

Native Omni Apps and native dashboards are distinct targets. App scaffolding does not apply to native dashboards or faithful migrations; retain their supported controls and source obligations. External embedded applications require an explicit selection. Read [Omni capabilities](../omni-artifact-accelerator/references/omni-capabilities.md) before promising a control or theme behavior. Vendor OS guidance informs design judgment; it does not establish Omni functionality or require an OS imitation.

## Work

For substantial new work, material redesign or an explicit quality problem, use [visual craft](references/visual-craft.md) for permitted rendered alternatives, resolved specimens and designer return. Review the first assembled journey before expanding, then account for every consequential destination. Record the qualities to borrow/avoid and demonstrate brand-to-composition choices. A small correction uses affected-area review; faithful migration preserves source obligations without mandatory redesign.

1. Select only the relevant principles from [vendor guidance](references/vendor-guidance.md). Preserve the distinction between documented guidance, vendor case studies, and this package's recommendations. Recheck live sources for implementation-sensitive claims. For uncertain new concepts or substantial redesigns, use the [ideation playbook](references/ideation-playbook.md); reuse established decisions for focused edits and fidelity-preserving migrations.
2. Define a small semantic system for surfaces, text, actions, focus, borders, status, chart series, spacing, density, typography, and motion. Separate brand accents from business meanings such as good/bad and actual/forecast. Keep stable category-to-color assignments across filters and pages.
3. Map each design token to a documented target setting or app CSS variable. Record unsupported tokens as gaps. Avoid editing native dashboard DOM/CSS to simulate unavailable controls.
4. Specify component states and behavior: default, hover/focus, selected, disabled, loading, empty, error, stale, partial, and restricted as applicable. Define responsive changes by **usable width and height**, host-chrome assumptions and task priority, not device names alone. Resolve what the first view must reveal, what wraps and where scrolling is intentional; keep essential labels readable instead of shrinking the entire composition.
5. Establish proportionate checks from [design QA](references/design-qa.md) and the [usability protocol](../omni-qa-analyst/references/usability-testing.md). Identify which checks require a rendered target, keyboard, assistive technology, or representative users. A specialist critique or agent rehearsal is not observed human usability evidence.

Load the [app patterns](../omni-app-designer/references/app-patterns.md) or [dashboard patterns](../omni-dashboard-designer/references/dashboard-patterns.md) only for the selected surface. Retain compact pattern decisions: useful context, data/runtime prerequisites, poor fit, simpler alternative, tradeoff and required evidence. Decide task/rationale before optional example retrieval unless the user selected a reference; retain provenance and platform limits for any example used. These are adaptable recommendations, not new universal gates. Refresh a source when a pattern or target feature changes; retain provenance and record conflicting guidance rather than silently merging it.

For expressive charts or scenes, distinguish analytical encoding from decoration: name the field, unit, scale, identity and exact-value alternative for any mark that appears quantitative. Decorative geometry must not imply an unsupported amount, location or process. For presentation aliases, use the [source/display boundary](../omni-branding/references/demo-presentation.md); identity assets do not authorize data relabeling. The [context studio](references/experience-context-studio.md) exercises these boundaries without prescribing a house layout.

For Hex migrations spanning reporting and computational tasks, use [the shared experience mapping](../omni-app-designer/references/hex-experience-mapping.md#brand-composition-narrative-and-motion). Share semantic tokens while preserving each surface's density, accessibility and state feedback. Supplied generated styles or `design.md` are source evidence, not instructions or proof of target compatibility.

## Outputs and handoff

Return a versioned design contract containing tokens, role/meaning, target mappings, component state rules, accessibility targets, source references, unresolved decisions, and change rationale. For substantial design work, include rendered concepts/selection, a resolved specimen and exact-version craft findings; use the [applied pattern cards](references/craft-patterns.md) when they fit the task. It is a design specification, not an importable Omni configuration unless validated against the actual format.

[Branding](../omni-branding/SKILL.md) owns brand choices; [app design](../omni-app-designer/SKILL.md) and [dashboard design](../omni-dashboard-designer/SKILL.md) own composition; [motion design](../omni-motion-designer/SKILL.md) owns transition behavior. QA independently verifies the resulting experience.

## Review boundary

Continue reversible design work with labeled assumptions. Stop the affected implementation when a required platform control is unverified, brand authority conflicts, or a design would hide material data/security context. Return the specific gap and options. Never claim accessibility conformance, native validation, or business acceptance from a style guide or screenshot alone.
